# Polyclaw 日本語化ガイド

## 概要

このディレクトリは、`polyclaw-jp` の日本語化作業における判断基準をまとめる場所です。

- `polyclaw-jp` は、GitHub Copilot SDK を使った本家 `polyclaw` の日本語特化フォークです。
- 本家の価値を取り込みながら、日本語ユーザーに自然な体験を提供することを目的とします。
- 上流追随戦略はハイブリッドです。
- コア層（`app/runtime/agent`, `server`, `state`）は、本家から cherry-pick します。
- UI 層（`app/frontend`, `app/tui`, `templates/`, `skills/`）は、完全独立で日本語 UX を最優先します。
- このディレクトリの全文書は、`polyclaw-jp` の日本語化作業における唯一の規範です。
- 迷った場合は、本文書から `glossary.md` と `style-guide.md` をたどり、PR レビューの判断基準として使います。

### この文書の使い方

- 新しい PR を作る前に、対象が日本語化対象か英語維持対象かを確認します。
- レビュー時は、まず本文書の境界線と各ドキュメントの規範を照合します。
- 用語、文体、絵文字、テスト方針の判断は、各リンク先の文書を優先します。
- 規範を変更する場合は、実装差分より先に `docs/i18n/` の文書を更新します。

## 大前提ポリシー

**「ユーザに見えるものは日本語、開発者しか見ないものは英語」** を、すべての PR レビューの判断基準とします。

この方針は、日本語ユーザーに自然な体験を提供しながら、本家 `polyclaw` との同期コストを抑えるためです。
UI、Bot、Voice、Toast、LLM 応答など、体験に直結する面は日本語化します。
一方で、ログ、シンボル、API key、内部 docstring など、開発者と連携システムだけが扱う面は英語を維持します。

## 英語維持境界線

| 対象 | 言語 | 理由 |
|---|---|---|
| 内部ログ（`logger.info("[agent.start]...")`） | 英語維持 | grep 性、OTel 互換、本家追随性 |
| Python docstring | 英語維持 | 本家コードと整合 |
| AGENTS.md 規約 | 英語維持 | Copilot CLI/Claude Code が読む |
| コード内コメント | 英語推奨 | 本家追随コスト |
| エラーコード/key 文字列 | 英語維持 | API consumer 互換 |
| 変数名/関数名/シンボル | 英語維持 | （自明） |
| API JSON のフィールド名 | 英語維持 | API consumer 互換 |
| Git commit メッセージ | 英語維持 | Conventional Commits 規約 |
| README.md | 日本語化 | エンドユーザー向け |
| docs/（Hugo サイト） | 日本語化 | エンドユーザー向け |
| CONTRIBUTING.md | 日本語化 | 日本語コミッター向け |
| ユーザ可視メッセージ（UI/Bot/Voice/Toast） | 日本語化 | 主目的 |
| LLM プロンプト（templates/） | 日本語化 | A 案の本質 |
| スキル（`SKILL.md`）本文 | 日本語化 | LLM が日本語で動作するため |

### 読む順序

1. まず本文書で、日本語化対象と英語維持対象の境界を確認します。
2. 次に `glossary.md` で、対象領域の訳語を確認します。
3. 文体や表記に迷う場合は、`style-guide.md` を確認します。
4. 作業対象の洗い出しには、`inventory.csv` を使います。
5. テスト更新やフェーズ判断は、`test-strategy.md` と `phase-plan.md` を参照します。

### 更新ルール

- 新しいユーザ可視文字列を追加した場合は、必要に応じて `inventory.csv` を更新します。
- 新しい訳語を採用した場合は、`glossary.md` に追加してから実装へ反映します。
- 文体ルールや絵文字ルールを変える場合は、`style-guide.md` を先に更新します。
- フェーズの完了条件が変わる場合は、`phase-plan.md` を更新します。

## 主要な意思決定（Quick Reference）

- **人格名 `Octo`（オクト）**：セットアップウィザードで選択します。
  - デフォルト候補は 3-5 個をウィザード内で提示します。
  - 単一の人格名をコードへ固定で埋め込まない方針です。
  - UI と LLM プロンプトの表示名は、選択結果に従います。
- **絵文字方針**：感情・状態・カテゴリのタグとしてのみ使用します。
  - 許可例は `✅ 完了 / ⚠️ 警告 / ❌ 失敗 / 📝 メモ / 🔍 検索` です。
  - 文末装飾としての絵文字は禁止します。
  - 絵文字は文頭または見出しで 1 つだけ使用し、日本語ラベルを併記します。
- **音声 voice**：Phase 1 完了時に実機検証します。
  - 検証候補は `nova`、`shimmer`、`alloy` です。
  - セットアップウィザードで選択可能にします。
  - 音声名は API 値として扱い、表示説明だけを日本語化します。
- **バージョニング**：A 案完了時に `v6.0.0-jp.1` へ bump します。
  - 日本語特化フォークとしての互換性境界を明確にします。
  - 以後の日本語化修正は、必要に応じて `-jp.N` を進めます。
  - Git commit メッセージ自体は英語維持です。

## 作業フェーズ（俯瞰）

日本語化作業は、事前準備フェーズから Phase 5 までを順に進めます。

1. **事前準備フェーズ**：規範、用語、対象範囲を固定します。
   - `docs/i18n/` の各文書を整備します。
   - 翻訳対象文字列を `inventory.csv` で棚卸しします。
2. **Phase 1（LLM）**：人格、プロンプト、スキル本文を日本語化します。
   - LLM の出力トーンを先に安定させます。
   - A 案の中核として、`templates/` と `skills/` を優先します。
3. **Phase 2（Frontend）**：Web UI の表示文言を日本語化します。
   - `app/frontend` の画面、Toast、セットアップウィザードを対象にします。
   - 文言は `glossary.md` と `style-guide.md` に合わせます。
4. **Phase 3（Backend）**：ユーザ可視の API 応答と Bot 文言を整理します。
   - 内部ログ、docstring、key 文字列は英語維持です。
   - エラーメッセージが UI に出る場合だけ、日本語化を検討します。
5. **Phase 4（TUI）**：Terminal UI の表示文言を日本語化します。
   - `app/tui` の表示、ヘルプ、状態ラベルを対象にします。
   - 開発者向け CLI 内部名は英語維持です。
6. **Phase 5（テスト + ドキュメント）**：テスト期待値と公開文書を整えます。
   - 日本語表示を前提に、E2E とスナップショット相当の期待値を見直します。
   - README、docs、CONTRIBUTING を日本語ユーザー向けに更新します。

この順序により、LLM の人格・語彙を先に固定し、その後に画面、API 境界、TUI、テストを安定させます。
Phase 1 の完了後に音声 voice の実機検証を行い、セットアップウィザードへの組み込み可否を判断します。
Phase 2 以降は、ユーザ可視面を優先し、開発者専用面を無理に翻訳しません。
Phase 1〜5 の想定 PR 数は合計 33（事前準備込み 34）です。
Phase 5 では、公開ドキュメントとテスト期待値が日本語化方針と一致していることを確認します。

### フェーズ別の主な成果物

| フェーズ | 主な成果物 | 完了の目安 |
|---|---|---|
| 事前準備 | 規範文書、用語集、インベントリ | レビュー基準が共有されている |
| Phase 1 | LLM プロンプト、スキル本文、人格候補 | 日本語応答の基本トーンが安定している |
| Phase 2 | Frontend 文言、セットアップウィザード、Toast | Web UI が自然な日本語で使える |
| Phase 3 | Backend のユーザ可視応答 | API 互換を保ちながら表示文言が整理されている |
| Phase 4 | TUI 文言、ヘルプ、状態ラベル | Terminal UI が日本語で理解できる |
| Phase 5 | テスト、README、docs、CONTRIBUTING | 日本語化後の品質確認が完了している |

## レビューチェックリスト

各 PR では、以下の観点を確認します。

- [ ] 用語集（`glossary.md`）と一致しているか。
- [ ] スタイルガイド（`style-guide.md`）に従っているか。
- [ ] 英語維持境界線（本文の表）と整合しているか。
- [ ] 用語ブレ（同じ概念に異なる訳語）がないか。
- [ ] 絵文字方針に違反していないか（文末装飾禁止）。
- [ ] 半角全角混植スペース規約を守っているか。
- [ ] ユーザ可視メッセージが英語のまま残っていないか。
- [ ] 開発者専用のログ、key、シンボルを不要に日本語化していないか。
- [ ] LLM プロンプトとスキル本文が日本語で自然に動作するか。
- [ ] API JSON のフィールド名やエラーコードの互換性を壊していないか。
- [ ] テスト期待値を日本語化後の表示に合わせて更新しているか。
- [ ] 差分が対象フェーズと一致しており、不要な領域を触っていないか。

### レビュー結果の扱い

- 境界線に迷う差分は、まず本文書の表へ戻って判断します。
- 用語の揺れは、実装側で吸収せず `glossary.md` を更新してから直します。
- 文体の揺れは、`style-guide.md` に沿って PR 内で修正します。
- 方針変更が必要な場合は、実装 PR とは分けて規範文書の更新を先行します。
